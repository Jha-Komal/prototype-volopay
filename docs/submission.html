2. Architecture

How data moves. The user fills an invoice in the browser, which stores it (browser storage in the prototype, Postgres in production). Run checks sends it to /api/check, the authoritative Volopay checks (V-01 to V-05). Only invoices that pass can be submitted. Submit calls the partner adapter, which calls the simulated provider endpoint. The provider returns accepted or rejected with a code. The API stores the response as a status event and the invoice page shows it in the timeline. Where validation happens: in the browser while typing (hints), on the Volopay API before sending (authoritative), and at the provider after sending (simulated rules).

3. Build vs partner decisions

Volopay builds: invoice creation, pre-send validation, status tracking and error handling, the receive-side matching, collections matching, and the accounting connectors. These sit close to the finance user and are where Volopay differentiates. The partner provides: the legal link to the tax system. In the UAE only an accredited provider may submit, so a partner is required. The prototype hides the provider behind one interface (PartnerAdapter) so a real accredited provider can replace the simulator by swapping one file. This follows the Challenge 1 strategy of adding e-invoicing to the AR and AP products. The named provider candidates come from the Challenge 1 research and should be inserted here. The prototype does not name any provider as connected.

5. Tools, assumptions, limitations, next steps

Tools: Next.js 16 (App Router), React 19, TypeScript, Tailwind 4, browser localStorage. Built with Claude Code, deployed on Vercel (add).

Assumptions: a TRN has 15 digits (secondary sources, not confirmed against the FTA); standard VAT is 5%; each line needs a VAT category; invoice numbers look like INV-0000 (invented). The Rules page marks every rule as sourced, assumed or simulated. The official KPMG/FTA field guidance could not be opened from the build environment, so the required-fields list covers a subset of the 51 mandatory fields and is not confirmed.

Limitations: single browser, no authentication, no multi-seller uniqueness, no PDF or XML output, no credit notes, no retry for temporary provider errors, English only, desktop-first.

Next steps to launch: (1) confirm rules against the FTA and Ministry of Finance sources; (2) select and contract an accredited provider and map the invoice model to its schema; (3) replace the simulator with the real adapter and handle async callbacks and retries; (4) move storage to a production database with audit trail; (5) add authentication and multi-tenant access; (6) build the accounting connectors; (7) security review and sandbox certification with the provider.
